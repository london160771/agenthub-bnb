1. PROJECT OVERVIEW AND PURPOSE
--------------------------------------------------------------------------------
AgentHub is a marketplace for AI agents on BNB Smart Chain, built for a BNB
hackathon as a polished, deployable Web3 SaaS MVP.

The product is organised as a six-step user journey, and the phases follow it:
  DISCOVER -> EVALUATE -> COMPARE -> HIRE -> EXECUTE -> VERIFY

The differentiator is HONESTY ABOUT DATA PROVENANCE. Every value shown to a user
carries a per-field badge saying where it came from: `chain` (read live from BNB
testnet), `derived` (arithmetic on chain data, with the assumption stated),
`input` (the user supplied it), `simulated` (modelled), or `unavailable`
(deliberately withheld rather than invented). This is the project's core claim and
its main defence; do not weaken it.

AS OF PHASE 7, NO EXECUTOR EMITS `simulated` ANY MORE (§8A). The tag and its
dotted-underline treatment are kept deliberately as machinery for anything future
that needs them. Do not mistake the absence of the tag for the absence of the
requirement — the next modelled number must still carry it.

Secondary theme: "Agent Advantage" — proving that hiring an agent beats doing the
task by hand, using measured numbers only.

7. IMPORTANT ARCHITECTURE / TECHNICAL DECISIONS
--------------------------------------------------------------------------------
A1. PER-FIELD PROVENANCE, NOT PAGE-LEVEL FOOTNOTES. Every output value carries
    its own badge. A simulated headline number also gets a dotted warn-coloured
    underline. Do not replace this with a single page disclaimer.

A2. output SHAPE (the contract between executors and the UI):
      { headline, summary, fields[], tables?[], warnings?[], recommendation,
        hasSimulated, provenance, reads[] }
    Each field: { key, label, value, source, tone?, note? }. Rendered by
    frontend/src/components/execution/ExecutionResult.jsx as a FLAT <dl>.
    Tables (T1.6, §8C) are optional { title, columns:{key,label,note?}[], rows:Record<key, {value,source,tone?,note?}|string>[], note?, emptyNote? }[]
    with per-cell provenance (string shorthand implies chain) and `overflow-x-auto` table renderer. Warnings are optional string[]. Execution.output is Schema.Types.Mixed, so the extension needed NO model change — but the renderer now exists.
    TWO LAYOUT CONSTRAINTS that are easy to break:
      - A field with `tone` renders its VALUE inside a Badge. Long values with a
        tone break the layout; keep toned values short and put detail in `note`.
      - The row is `flex flex-wrap items-baseline justify-between`, so a long
        label plus its provenance badge wraps the value onto the next line
        instead of overflowing. Verified at 390px.

A3. CATEGORY COUPLING IS SIX PLACES, and all must change together to add one:
      backend/models/Agent.js             AGENT_CATEGORIES
      frontend/src/config.js              CATEGORIES
      frontend/src/lib/hire.js            HIRE_FIELDS
      backend/services/agentExecutors.js  EXECUTORS + ADDRESS_INPUTS
      backend/data/seedAgents.js
      frontend/src/pages/LandingPage.jsx  CATEGORY_ICONS  (easy to miss;
                                          falls back to `Compass`)
    Category FILTERING and COUNTING are fully generic off AGENT_CATEGORIES and
    need no change.

A4. Mongoose exclusion projection PROJECTION = '-__v -_id' means any new schema
    field is AUTOMATICALLY exposed by the API. Convenient, but it also means a
    half-finished field leaks. Be deliberate.

A5. SUB-DOCUMENT DEFAULTS HAZARD. Execution.advantage MUST keep `default: null`
    and MUST NOT have subfield defaults. A sub-document default makes Mongoose
    materialise an empty object on every hire, which reads downstream as "a
    measurement was taken and came back zero". This is load-bearing.

A6. AdvantageSchema enforces three rules on purpose: no defaults on any field;
    provenance (manualMethod, evidenceRef, measuredBy, measuredAt) required if
    the object exists at all; a metric cannot appear without its definition
    (stepDefinition with step counts, qualityRubric with quality scores).

A7. BigInt-only arithmetic for chain values (see weiToDecimalString in
    blockchainService.js). Never use floats for token amounts or wei.

A8. Backend input validation is STRUCTURAL ONLY, by deliberate trade-off.
    executionController.js: MAX_INPUT_KEYS = 12, MAX_INPUT_VALUE_LENGTH = 500,
    MAX_TASK_LENGTH = 300, and parseInput accepts ONLY string/number/boolean
    primitives — no arrays, no nested objects. Category-specific rules live in
    the frontend where the field schema is, because duplicating them server-side
    would guarantee drift.

A9. Retry is folded into POST /api/executions/:id/run. THERE IS NO /retry ROUTE.
    `failed` -> resetForRetry then re-run; `running` -> started:false;
    `completed` -> 409.

A10. config/env.js is the single place to read process.env. Known violation:
     blockchainService.rpcUrl() reads process.env.BNB_TESTNET_RPC_URL directly.
     Worth fixing when next touching that file.

A11. provenanceHost exposes only the RPC HOSTNAME, never the full URL, because a
     configured RPC URL can carry an API key.

THE DELETION THAT MATTERED MOST
lendingProtocolAdapter.js used to derive health factor, collateral and borrow from
an FNV-1a hash of the wallet address whenever no verified deployment was on file.
That path is GONE, not disabled and not kept as a fallback. Either Venus is read
on-chain, or the caller is told the protocol is unsupported and why. Do not
reintroduce a "plausible default" here under any name.

WHY THE HEALTH FACTOR IS `derived` AND NOT `chain`
Venus is a Compound fork and stores NO health factor. It exposes
getAccountLiquidity(account) -> (error, liquidity, shortfall) in 1e18 USD.
shortfall > 0 means the account is liquidatable RIGHT NOW, and that verdict is
treated as authoritative over anything we compute. The ratio we report is
liquidation-weighted collateral / debt, assembled from per-market reads.

*** THE RECONCILIATION IS LOAD-BEARING. DO NOT REMOVE IT OR LOOSEN IT. ***
Before reporting a derived health factor, the adapter re-derives Venus's OWN
liquidity/shortfall pair from our per-market numbers and requires EXACT equality.
One wei of disagreement withholds the number. This is not test scaffolding — it
runs on every execution.
It earned its place: the per-market weight was first read from markets() word[1],
the borrowing-power collateral factor (0.70 for vBNB). Everything looked right and
the answer looked plausible. Reconciliation was out by $0.60, which forced a
second look — getAccountLiquidity actually applies the HIGHER LIQUIDATION
THRESHOLD in word[3] (0.80). Shipping word[1] would have overstated danger on
every position in the product. A tolerance instead of exact equality would have
hidden it. Compound also truncates at EVERY multiplication, so reproducing Venus's
exact operation order is what makes exact equality achievable at all.

RISK R1 IS RESOLVED (getAccountSnapshot's tuple layout)
The layout was PROVEN, not assumed: member 4 is the exchange rate, which is also
readable alone via exchangeRateStored(). Across all 39 markets returning four
words the two agreed byte-for-byte with NON-ZERO values — 39 confirmations, no
mismatches, no vacuous zero-equals-zero cases. On the ten delegator markets the
rate sat at the same index with the extra words zero. Then the balances were
validated end to end by reproducing getAccountLiquidity to the wei on a real
position. Venus's legacy delegator proxies return EXTRA WORDS, so abi.js's decoder
takes the leading words and REQUIRES every extra word to be zero, throwing
otherwise — a wrong selector on a proxy can otherwise silently return a decodable
number from a different function.
