2. ON-CHAIN VERIFICATION I PERFORMED MYSELF (read-only, chain 97)
--------------------------------------------------------------------------------
Method: two throwaway read-only probes against
https://bsc-testnet-dataseed.bnbchain.org, at blocks 127,334,373 / 127,334,563 /
127,334,773. Both probe files were deleted after running. No signing, no
transaction, no key material. 122 RPC calls total.

Why probes were necessary: the repo has no keccak256 (backend/package.json has no
ethers/web3), so function selectors could not be COMPUTED. They were recalled and
then validated EMPIRICALLY — a call returning well-formed, plausible data is the
evidence. Anything that reverted is excluded from this plan.

2c. ORACLE PRICE SCALING — verified, and it is a trap:
  Venus/Compound scale prices as 1e(36 - underlyingDecimals). Confirmed across
  three different decimal values, which is why this is stated as fact:
    vUSDC  underlying 6 decimals  -> $1.00
    vDOGE  underlying 8 decimals  -> $0.0865
    vBUSD  underlying 18 decimals -> $1.0012
  Reading the raw word without normalising by the UNDERLYING token's decimals
  produces $1,000,000,000,000 for USDC. Any implementation must read
  underlying() -> decimals() first.

2d. *** THE MOST IMPORTANT HONESTY FINDING IN THIS AUDIT ***
  Testnet oracle prices are REAL CHAIN READS but they are NOT MARKET PRICES:
    vBNB   $600.00
    vBTC   $2,100,000.00      <-- roughly 20x any real BTC price
    vUSDT  $0.50              <-- a stablecoin, priced at fifty cents
    vETH   $2,464.94
    vXVS   $3.06
  These are testnet oracle values. They are genuinely read from chain 97 and are
  correctly labelled `chain` for provenance, but presenting them as market prices
  would be a fabrication of a different kind — technically sourced, materially
  false. Every USD figure derived from them MUST carry an explicit
  "testnet oracle price, not a market price" caveat in the UI, not just a
  provenance badge.
  Also: getUnderlyingPrice FAILED for vMATIC. Per-market price failure is a
  normal case and must degrade to `unavailable` for that row, not abort the run.

2e. RATES -> APY is DERIVED, never `chain`:
  Turning supplyRatePerBlock into an APY requires a blocks-per-year assumption.
  BSC targets ~3s blocks => 10,512,000 blocks/yr. That is an assumption, so the
  APY is `derived` and the assumption must be printed. Simple (non-compounding)
  APR from live testnet rates:
    vETH   supply 15.72%   borrow 16.69%
    vBNB   supply  5.28%   borrow  7.54%
    vSXP   supply  1.73%   borrow  1.85%
    vXVS   supply  0.48%   borrow  3.11%
    vBUSD  supply  0.00%   borrow  0.29%
    vUSDT  supply  0.00%   borrow  0.00%
  Real, differentiated, rankable data. This is what makes Yield genuinely
  implementable.

    Existing reads are all "free" JSON-RPC: eth_chainId, eth_blockNumber,
    eth_gasPrice, eth_getBlockByNumber, eth_getBalance, eth_getTransactionCount,

    Types are only: address | number | select | text | textarea. Rebalancing

    and parseInput accepts only string/number/boolean primitives — no arrays, no
    nested objects. A repeatable allocation list cannot currently be submitted.

    output.hasSimulated, output.provenance and output.reads[] are the whole

4. SHARED INFRASTRUCTURE (the architectural rule: build once, not four times)
--------------------------------------------------------------------------------
All four categories reduce to the same five primitives. Build these FIRST; the
four agents then become thin, mostly-arithmetic layers on top.

S1. backend/services/abi.js  [NEW]
    Minimal encode/decode. encodeCall(selector, args), decodeUint, decodeAddress,
    decodeBool, decodeAddressArray, decodeString, and a fixed-point helper
    (BigInt only). ~120 lines, no dependency. Selectors stored as verified
    CONSTANTS with a comment recording that they were empirically validated
    (Section 2b) — never computed at runtime, since there is no keccak.

S2. blockchainService.ethCall(to, data)  [ADD to existing file]
    One function. Goes through the existing rpcCall, so it is automatically
    counted by the AsyncLocalStorage RPC meter from Phase 6.5 and appears in
    output.reads[] and rpcCallCount for free. This is why Phase 6.5's
    instrumentation was worth doing first.

S3. backend/services/venusAdapter.js  [NEW — the single biggest win]
    Wraps the verified deployment. Exposes:
      listMarkets()            -> the 49 vTokens, cached per run
      marketInfo(vToken)       -> symbol, vDecimals, underlying, uDecimals,
                                  collateralFactor, isListed
      oracleAddress()          -> READ from the Comptroller, never hardcoded
      priceUsd(vToken)         -> normalised by 1e(36-uDecimals); returns
                                  {value, source:'chain', caveat:'testnet oracle
                                  price, not a market price'} or null on failure
      accountLiquidity(addr)   -> {error, liquidity, shortfall}
      assetsIn(addr)           -> vTokens the wallet has entered
      ratesFor(vToken)         -> supply/borrow per-block rates
    Serves Health Factor, Yield, Rebalancing (prices) and Grid (reference price).
    ONE adapter, FOUR categories. This is the answer to the architectural rule.

S4. backend/services/tokenService.js  [NEW]
    BEP-20 balanceOf / decimals / symbol via S1+S2. Unblocks the
    long-standing "token positions unavailable" gap in portfolio AND supplies
    Rebalancing's current holdings.

S5. backend/services/calc.js  [NEW]
    Pure, unit-tested arithmetic, no I/O: driftVsTarget, gridLevels,
    ratePerBlockToApr(rate, blocksPerYear), usdValue(amount, decimals, price),
    healthFactorFrom(...). Pure functions are the only part of this plan that can
    be tested without a network.

S6. output schema extension  [ExecutionResult.jsx + executors]
    Add ONE optional key: output.tables = [{ title, columns[], rows[],
    rowSources[] }]. Backwards compatible — existing executors emit no tables
    and render unchanged. Per-cell/per-row provenance preserved. Serves the trade
    list, the grid ladder, and the ranked pool list.

S7. provenance
    Reuse SOURCES / field() / buildProvenance() from agentExecutors.js unchanged.
    ADD one new source value: 'oracle' — or keep 'chain' plus a mandatory
    `caveat` string. Recommendation: 'chain' + caveat, because the read genuinely
    is a chain read and inventing a source class understates that; the caveat
    carries the "not a market price" warning. Decide before coding.

5. CATEGORY 1 — HEALTH FACTOR MONITORING
--------------------------------------------------------------------------------
1. CURRENT STATE
   Complete product flow already exists: 2 seeded agents
   (venus-health-guardian protocols['Venus'], radiant-liquidation-shield
   protocols['Radiant']), HIRE_FIELDS (position wallet, protocol, warn-below
   threshold), runHealthFactor executor, result page with risk bands
   (CRITICAL<1.1, HIGH<1.35, MEDIUM<1.8, LOW). Real: wallet native balance,
   block, gas price, threshold arithmetic. SIMULATED: the health factor,
   collateral, borrow — i.e. the answer.

2. WHAT IS MISSING
   Only the data source. lendingProtocolAdapter.DEPLOYMENTS is empty, so
   readHealthFactor returns a deterministic FNV-1a hash of the address.

3. REAL DATA REQUIREMENTS
   Available now (already in the app): wallet native balance, block, gas price.
   Available with current testnet RPC + eth_call: Comptroller getAssetsIn,
     getAccountLiquidity, markets(vToken)->collateralFactor; vToken
     getAccountSnapshot (LAYOUT UNCONFIRMED), exchangeRateStored, decimals,
     symbol, underlying.
   Requires eth_call: all of the above. THIS IS THE ONLY BLOCKER.
   Requires a verified protocol address: SATISFIED for Venus (Section 1+2).
     NOT satisfied for Radiant — no verified Radiant testnet address exists on
     file, and I did not verify one.
   Requires a price feed: yes for a USD-denominated health factor — SATISFIED via
     Comptroller->oracle->getUnderlyingPrice, with the 2d caveat.
   Unavailable on testnet: nothing material.
   NO ADDRESSES INVENTED. Radiant stays unsupported until verified.

4. EXISTING CODE WE CAN REUSE
   Everything. lendingProtocolAdapter.js is the seam; riskBand() unchanged;
   both agents' hire forms unchanged; ExecutionResult unchanged (flat fields
   suffice); provenance unchanged. Only `source` flips simulated -> chain.

5. AGENT REQUIREMENTS
   venus-health-guardian must genuinely read the wallet's Venus position. If the
   wallet has NO Venus position (the common case on testnet), it must say
   "no position found on Venus core pool at block N" — a real, useful,
   verifiable answer — NOT a modelled number.
   radiant-liquidation-shield MUST be paused or relabelled. Leaving it `live`
   claiming Radiant coverage with no verified Radiant address is exactly the
   dishonesty this project has been avoiding.

6. HIRE FLOW
   Required: position wallet (address, prefills from connected wallet).
   Optional: protocol (from agent.protocols — restrict to Venus), warn-below
   threshold (default 1.5, min 1.0, max 10).
   Validation: unchanged. Defaults: unchanged.
   Output expectation: real health factor, or an explicit "no position" result.
   Fits the existing architecture with ZERO hire-flow changes.

7. EXECUTION FLOW
   input -> validate address -> assertTestnet -> getAssetsIn(wallet) ->
   if empty: emit "no position" result and stop (cheap, honest) ->
   else per asset: markets()->collateralFactor, getAccountSnapshot,
   oracle price, underlying decimals -> compute collateral USD and borrow USD ->
   healthFactor = (sum collateralUsd * cf) / sum borrowUsd -> risk band ->
   threshold comparison -> result + provenance. RPC count is metered
   automatically (S2).

8. OUTPUT
   healthFactor            derived  (from chain reads; formula printed)
   collateralUsd           derived  + testnet-oracle caveat
   borrowUsd               derived  + testnet-oracle caveat
   per-asset table         chain    (S6 table; amounts chain, USD derived)
   collateralFactor        chain
   liquidity / shortfall   chain
   riskBand                derived
   thresholdBreached       derived
   warnThreshold           input
   walletNativeBalance     chain
   block / rpcHost / time  chain    (buildProvenance)
   Radiant, if requested   unavailable

9. AGENT ADVANTAGE COMPATIBILITY
   YES — and this UNBLOCKS a category AGENT_ADVANTAGE.md §7 currently lists as
   ineligible. Once the health factor is a chain read it scores properly on the
   Provenance dimension.
   Proposed experiment: for a testnet wallet with a real Venus position,
   determine its health factor and whether it breaches 1.5. Manual method: open
   the Venus testnet app / testnet.bscscan.com, read each entered market's
   supplied and borrowed balance, read each collateral factor, read each oracle
   price, and compute the ratio by hand. That is a genuinely laborious manual
   task across many contract reads, which is exactly the shape that makes the
   comparison meaningful.
   NO BENCHMARK NUMBERS ARE STATED HERE. Nothing is measured until a human runs
   both halves and records evidence per AGENT_ADVANTAGE.md §6.
   PREREQUISITE: a testnet wallet that actually holds a Venus position. If none
   is available the experiment cannot run, and that must be reported, not faked.

10. DIFFICULTY / TIME
    MEDIUM. Needs S1+S2+S3. The one genuine unknown is the 6-word
    getAccountSnapshot layout, which must be confirmed on testnet.bscscan.com
    before decoding. Highest value per unit of effort in the whole plan, because
    it removes the ONLY simulated data in the entire system.

11. HACKATHON VALUE
    HIGHEST. It is a spec Tier-1 category, a required hackathon category, and it
    converts the project's single biggest honesty liability into its strongest
    proof point. Also the best Agent Advantage candidate.

     using it. This is the honest resolution — AgentHub does not need a token
     allowlist it cannot verify. Venus underlying addresses are additionally
     available as verified suggestions via S3.
   Requires a price feed: for USD-valued drift, yes. Available for
     Venus-listed assets only, with the 2d caveat. For any asset Venus does not
     list, USD valuation is `unavailable`.
   Unavailable on testnet: meaningful market prices (2d).
   RECOMMENDATION: ship TOKEN-UNIT drift as the primary output and USD drift as a
     clearly-caveated secondary. Token-unit drift needs no price at all, so it is
     unimpeachable; USD drift is a bonus that degrades gracefully.

4. EXISTING CODE WE CAN REUSE
   Gas estimation (SWAP_GAS_UNITS = 150,000), affordability, the `input`
   provenance class, the field renderer, and runTrading's contract-verification
   step. Needs S4 (token balances) and S6 (trade table).

5. AGENT REQUIREMENTS
   rebalance-advisor must return an actual trade list: per asset, current weight,
   target weight, drift, and a BUY/SELL action with a size. A portfolio report is
   not a rebalancing plan. PLAN-ONLY — it computes trades, never submits them,
   consistent with how `trading` already behaves.
   IMMEDIATE ACTION REGARDLESS OF SCHEDULING: this agent must not stay `live`
   with a rebalancing tagline while returning a portfolio report. Build it or
   relabel it.

6. HIRE FLOW
   Required: wallet to rebalance (address, prefills); target allocation.
   ALLOCATION INPUT — the one real UI decision. F3/F4 mean there is no repeatable
   field type and no array support in the backend. Two options:
     (a) NEW repeatable field type in hire.js + array support in parseInput.
         Correct long-term, more work, touches validated request-handling code.
     (b) A single `text` field holding "0xToken:40,0xToken:35,0xToken:25",
         parsed and validated server-side. Zero schema change, zero new field
         type, fits MAX_INPUT_KEYS = 12 immediately.
   RECOMMENDATION: (b) for the hackathon, with a clear placeholder, inline help
   and precise parse errors. (a) is the post-hackathon refactor.
   Optional: drift tolerance % (default 5), include-native toggle, notes.
   Validation: each address matches ADDRESS_RE and has bytecode; weights are
     numbers; weights sum to 100 +/- 0.01; at least 2 assets; at most 8 (bounds
     the read count).
   Output: drift + trade list in token units; USD where a price exists.

7. EXECUTION FLOW
   input -> parse allocation string -> validate addresses and weights ->
   assertTestnet -> per asset: eth_getCode (reject non-contracts), decimals,
   symbol, balanceOf -> native balance -> compute current weights (token-unit
   basis, and USD basis where every asset has a price) -> drift vs target ->
   trades needed, sized -> gas per trade at live gas price -> total gas ->
   result + provenance.

8. OUTPUT
   holdings table          chain (balances, decimals, symbols)
   currentWeights          derived
   targetWeights           input
   drift per asset         derived
   trade list table        derived (action, asset, size in token units)
   usdValues               derived + testnet-oracle caveat, or unavailable
   gasPerTrade / totalGas  derived (150,000-unit assumption stated)
   gasPrice                chain
   walletNativeBalance     chain
   driftTolerance          input
   slippage / actual execution price / routing   unavailable
   block / rpcHost / time  chain

9. AGENT ADVANTAGE COMPATIBILITY
   YES, but WEAKER than Health Factor or Yield, and it should not be one of the
   three experiments. Reason: the target allocation is user input, so much of the
   "work" is arithmetic on numbers the human already supplied, which flatters the
   agent. The genuinely laborious part (reading N token balances and decimals) is
   real but thin. If a fourth experiment were ever run, it would be this.
   NO NUMBERS FABRICATED.

10. DIFFICULTY / TIME
    MEDIUM-HARD — the hardest of the four, because it is the only one needing UI
    and request-validation changes (F3/F4), not just backend reads. Option (b)
    reduces it to MEDIUM.

8. CATEGORY 4 — GRID TRADING
--------------------------------------------------------------------------------
1. CURRENT STATE
   NOTHING EXISTS. No category, no agent, no executor, no hire fields, no UI, no
   icon. Absent from all six wiring points (F6) and from all 17 seeded agents.

2. WHAT IS MISSING
   All of it: category enum entry, icon, HIRE_FIELDS, executor, seeded agent(s),
   and a ladder renderer.

3. REAL DATA REQUIREMENTS
   Available now: wallet native balance, gas price.
   Available with current RPC + eth_call: token decimals/symbol/balanceOf;
     eth_getCode contract verification.
   Requires eth_call: yes.
   Requires a verified DEX router/pair address: NO verified PancakeSwap testnet

     1). getReserves() is therefore UNTESTED and NOT used in this plan. NO
     ADDRESS INVENTED.
   Requires a price feed: yes, to centre the grid. TWO honest options:
     (i) Venus oracle price for a Venus-listed asset — provenance `chain`, with

     (ii) A user-supplied reference price — provenance `input`.

     fall back to (ii) otherwise, and always state which was used.
   Unavailable on testnet: real order books, DEX routing, liquidity depth,

4. EXISTING CODE WE CAN REUSE
   A LOT — this is the cheapest of the four. runTrading already verifies a token
   contract, reads a balance, and estimates swap gas at a live gas price. The
   grid executor is that plus level arithmetic. Address validation, provenance,
   the field renderer, TaskInputError and assertRunnableInput all apply
   unchanged. Needs S6 for the ladder table.

5. AGENT REQUIREMENTS
   A new grid-strategy-planner agent that returns an actual GRID: every price
   level, the order size at each level, the side (buy below reference, sell
   above), total capital committed, and total estimated gas. Not a generic
   trading report.
   PLAN-ONLY, stated prominently: AgentHub prepares the grid and never places,
   signs or submits an order. This is consistent with existing `trading`
   behaviour and with the spec's explicit "do NOT spend time on full trading
   automation / high-risk financial execution".

6. HIRE FLOW
   Required: token address; upper bound; lower bound; grid levels (int);
     capital per level.
   Optional: reference price (blank => read from Venus oracle if listed);
     side bias; notes.
   Validation: address shape + has bytecode; lower > 0; upper > lower; levels
     between 2 and 50 (bounds output size and read count); capital > 0;
     reference price, if given, must sit between lower and upper — otherwise the
     grid is entirely one-sided, which is a user error worth catching.
   Defaults: levels = 10.
   Output: the full ladder plus capital and gas totals.

7. EXECUTION FLOW
   input -> validate bounds and levels -> assertTestnet -> eth_getCode on the
   token -> decimals, symbol -> balanceOf -> reference price (oracle or input;
   record WHICH) -> compute evenly-spaced levels between lower and upper ->
   assign side per level relative to reference -> size per level -> total capital
   -> gas per level at live gas price -> total gas -> fundability vs balance ->
   result + provenance.

8. OUTPUT
   grid ladder table       derived (level price, side, size)
   referencePrice          chain + testnet-oracle caveat, OR input — labelled
   priceSource             derived (says explicitly which of the two was used)
   levels / spacing        derived
   totalCapital            derived
   gasPerOrder / totalGas  derived (150,000-unit assumption stated)
   gasPrice                chain
   tokenSymbol / decimals  chain
   walletBalance           chain
   bounds, levels, capital input
   fill probability / slippage / liquidity depth / actual execution
                           unavailable
   block / rpcHost / time  chain

9. AGENT ADVANTAGE COMPATIBILITY
   NO — and it should be excluded. The grid is arithmetic on user-supplied bounds
   and level count. A human with a spreadsheet reproduces it quickly and exactly,
   so a favourable time comparison would be measuring "we wrote a loop", not a
   research advantage. AGENT_ADVANTAGE.md already excludes categories whose core
   value is not a real research finding; this belongs in that group. Excluding it
   is the honest call and is itself worth stating in the submission.

  (health-factor 2, monitoring 3, yield 3, trading 3, portfolio 3, research 3).

  Every one has erc8004Id: null, ownerAddress: '' and endpoint: ''.
  There is NO off-AgentHub agent in the system, and no code path that would
  execute one — agentExecutors.js dispatches on CATEGORY to six local functions.

WHICH ARE INTENDED TO REPRESENT REAL BSC AGENTS.

  source='indexed' BSC Mainnet discovery records from Phase 8. seedAgents.js's own header states that
  erc8004Id/ownerAddress are left empty on purpose, and that `verified: true`

  ERC-8004 verification. frontend/src/config.js SOURCE_LABELS renders
  'seeded' as "AgentHub demo data" (warn tone) and reserves "Verified on-chain"
  for 'verified'. So the honesty plumbing already exists and is correctly wired;
  Phase 8 now supplies indexed real-agent data; independent identity and task
  execution verification remain future work.

8004SCAN STATUS — UPDATED AFTER PHASE 8.
  `backend/services/scan8004Client.js` and `backend/scripts/ingest8004.js`
  provide read-side indexed discovery for BSC Mainnet chain 56, with optional
  `SCAN8004_API_KEY` support. Indexed records are discoverable/watch-only unless
  a separate execution verification is recorded. AgentHub still has no owned
  on-chain ERC-8004 identity verifier or registry-contract reader.
  Earlier versions of this document described the pre-Phase-8 state; that
  historical conclusion is superseded by the current client/importer above.

WHAT WOULD NEED TO CHANGE FOR INDEPENDENT ERC-8004 IDENTITY VERIFICATION.
  (Discovery is already integrated; the following is the remaining verification
  work, not a claim that 8004scan ingestion is absent.)
  1. A verified ERC-8004 registry address for the target network, plus its ABI
     and event names — none of which are on file, and none of which may be
     guessed (AGENTS.md).
  2. A new backend/services/erc8004Service.js reading identities via the same
     S1/S2 primitives, so its reads are metered like every other read.
  3. An indexer/importer writing Agent documents with source 'indexed' or
     'verified' and a populated erc8004Id.
  4. Trust score handling for externally-sourced agents — trustScoreService.js
     currently scores AgentHub-shaped metrics that an external agent will not have.
  5. Provenance: SOURCE_LABELS already distinguishes the classes; the seeded set
     must remain visibly 'seeded' rather than being silently upgraded.

CAN THE ARCHITECTURE SUPPORT BOTH EXTERNAL AND OWN AGENTS? YES, mostly.
  Supports it already: AGENT_SOURCES has 'verified'/'indexed' alongside
  'seeded'/'demo'; erc8004Id, ownerAddress and endpoint fields exist; the
  exclusion projection auto-exposes new fields; category filtering/counting is
  fully generic.
  Blocks it: agentExecutors.executeForAgent dispatches on category to a LOCAL
  function and THROWS on an unknown category. A real external agent would need to
  be called at its `endpoint` instead. That is a genuine architectural addition —
  an execution-strategy branch (local executor vs remote endpoint) — not a config
  change. The field exists; the code path does not.

MINIMUM REAL AGENTS TO AIM FOR PER CATEGORY.
  I cannot responsibly give a number, because it depends entirely on how many
  real BNB agents the ERC-8004 registry actually contains — which is exactly what
  is unverified. What I can say from the repo: AGENTHUB_SPEC.txt states "Do NOT
  build dozens of new AI agents. Use existing BNB/ERC-8004 agents wherever
  practical." Read against the current state (0 real agents, 17 seeded), the
  defensible target is: ONE genuinely real, verifiably-identified agent
  end-to-end is worth more than a large imported set, because it proves the
  integration path while the seeded catalogue stays honestly labelled 'seeded'.
  Set the real target only after the registry is verified.

11. RISKS
--------------------------------------------------------------------------------
R1. getAccountSnapshot returns 6 words, not the expected 4. Decoding it on an
    assumed layout would silently produce WRONG health factors — worse than a
    labelled simulation. Confirm on testnet.bscscan.com first.
R2. Testnet oracle prices are not market prices (2d). The mitigation is a
    mandatory caveat everywhere a USD figure appears. If that caveat is skipped,
    this plan makes the honesty problem worse, not better.
R3. Yield's ~300-call sweep is slow and rate-limitable. Cap the candidate set and
    log what was dropped.
R4. Most testnet wallets hold no Venus position, so the honest "no position
    found" path is the COMMON path, not the edge case. Build and demo it first.
R5. getUnderlyingPrice already fails for vMATIC. Per-market failure must degrade
    to `unavailable` for that row, never abort the run.
R6. Selectors are recalled and empirically validated, not computed. Any selector
    not in the confirmed list (2b) must be validated the same way before use.
    getReserves() specifically is UNTESTED.
R7. Scope. Nine Tier-1 items is a lot. T1.4 (the honesty relabel) is ~30 minutes
    and must land even if nothing else does.
R8. F9 remains unresolved by design and is the user's decision.
